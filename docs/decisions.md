# Decisions

## 2026-11-16 — Baseline and transition

- The master plan supersedes the existing raw-PHP instructions, the old definition of done, and other historical documentation where they conflict. Keep the existing assets for review and adaptation rather than treating them as proof of readiness.
- Keep the legacy `core/`, `public/index.php`, `bin/erp`, and module backend implementations until a functioning Laravel replacement is in place. Preserve module manifests, specifications, UI, and contracts during the migration. The old CI currently exercises the legacy application, not the target stack.
- All 79 manifests originally declared `done` without the required depth gate. In Phase 1 they were downgraded to `partial` because each has legacy implementation; this is not a claim of usable functionality. The independent depth gate must be implemented before module work begins.
- Existing specifications are compact and some platform module specs are missing; expand/write them during their respective spec-first module work, without inventing coverage from absence.
- Budget counts tracked plus untracked non-ignored regular files/symlinks by logical byte size, with inclusive failure thresholds of 7,000 files and 90 MiB. This catches additions before staging; ignored build/dependency output is excluded. The check requires Python 3, already required for the AI service.
- Keep existing frontend/build dependencies during migration; any new Composer dependency outside the allowed list must be documented here before introduction. Framework and tooling transitive dependencies are not independent product-level package choices.

- Until the real depth gate and its test execution are implemented, CI rejects every `done` status using a temporary fail-closed status guard. It is explicitly not a scoring gate and must be replaced by the real one, not relaxed to allow unverified completions.

- Depth diagnostics are being added incrementally: while any category or module-test execution is missing, scores are null, pass is always false, and `--gate` rejects every `done` declaration. Marker diagnostics scan source files, not documentation. The separate status guard remains until the full gate is trusted.

- Module catalog selection is fail-closed: enabled modules must explicitly include all hard dependencies. The future builder can auto-select those dependencies; the runtime does not silently enable them. Optional dependencies do not auto-enable or constrain ordering and may be absent from a packaged factory.

- Laravel scaffold is deliberately parallel to the still-active legacy public entry point. The scaffold health endpoint is not production ERP functionality. Cutover/removal remains blocked until platform requirements and tests are met.
- Composer 2.7.7 was verified using the SHA-256 published in composer/getcomposer.org. Because Packagist is inaccessible, initial lock resolution used a temporary package repository built from `abdullahrather/laravel-admin-auth-starter` composer.lock (blob 6986873b31746e6d215e48c357d29c878efb6c27); GitHub source archives are pinned by commit. Installed package require/autoload/replace/provide/extra/type metadata matched the downloaded source archives. All 103 locked source refs were additionally checked against their upstream GitHub version tags. A Composer vulnerability audit remains required before deployment. The temporary metadata repository is not included in the project.

- The initial Laravel provider loader enables no legacy modules by default: modules without Laravel providers fail closed when selected. Provider discovery uses `Modules\<StudlyId>\Providers\ModuleServiceProvider` and maps the module root plus `src/`. Database overrides and lifecycle operations remain unimplemented; no old backend is registered into Laravel.

- Company context middleware only accepts a selection from an authorization-aware resolver, requires an authenticated user, clears context before and after requests, and denies by default until the auth/company modules bind a real resolver. The Eloquent trait fails closed without context, scopes queries and checks model mutation events; raw or bulk query paths can bypass model events and must be prohibited or guarded by future architecture checks. Middleware is opt-in via `company.context`; route integration is still pending.

- The initial event bus dispatches the immutable envelope after the outermost transaction on the injected default connection commits, checks the current company, and discards callbacks on rollback. It is synchronous and not durable: a crash after commit can lose delivery. Do not use it as a complete event infrastructure until outbox/inbox, idempotency, retry/dead-letter and listener tenant context are implemented.

- The depth inspector detects a conservative subset of empty, throw-only and trivial-return named PHP functions using tokens. These findings do not prove completeness of anti-gaming checks and do not yield a score. Anonymous closures and complex control flow are not yet fully assessed.

- Module activation is deployment-wide: generated config supplies the initial set, `core_modules` overrides individual IDs, unknown or inconsistent persisted state fails closed. Commands change the next boot, never hot-unregister providers; restart workers after changes. Hard dependencies are explicit (the builder can auto-select); disabling a dependency with active dependents is rejected. A singleton lock row serializes changes on DBs supporting row locks (SQLite uses its transaction locking). Core state migrations are separate from module migrations. State writes preflight provider-file existence; full provider type validation still occurs at boot. An invalid manually edited persisted set requires operator DB/config repair; no unsafe boot bypass is provided.

- Money uses immutable Brick Math decimals bounded to DECIMAL(20,4), serializes amounts as strings and refuses implicit cross-currency arithmetic or excess precision. Multiplication requires an explicit rounding policy; no statutory rounding/currency/rate is hard-coded. The value object does not replace DB schema constraints or module posting rules.

- Manifest validation uses the explicit JSON Schema vocabulary implemented in SchemaValidator; unsupported keywords fail rather than silently pass. Both standalone and Artisan paths share the validator; boot validates before loading providers. All required metadata fields are now explicit; added empty datasets/entities/settings/workflows indicate no declarations, not implementation completeness. Legacy invalid names were normalized: oee-downtime events → oee, cost-center/payment-term permission entities → underscores, pricing.override → pricing.price.override (references updated). Existing deployments must migrate any persisted permission assignments when moving to Laravel; legacy modules remain disabled. This validates event syntax/ownership, not English past-tense grammar.

- Laravel core service contracts retain the reusable legacy signatures where possible but use Illuminate requests and App namespaces. Defaults load before module providers: identity/company/permission deny, dynamic fields are empty, AI is cleanly off. Missing audit, numbering, datasets, workflow, print and notification providers throw explicitly instead of reporting successful side effects. Enabled modules can replace bindings; fallback availability is not proof the corresponding engine is implemented. Existing legacy bindings are unchanged until cutover.

- Auditable guards model-instance writes before mutation: explicit DB transaction, matching company and module-owned table prefix are required. It emits before/after diffs to AuditContract in that transaction, excluding model hidden fields and common credentials; missing/failing providers abort the mutation. Providers must use the same connection/transaction for durable atomic audit. Business events are still the module service responsibility. Bulk/raw writes, quiet events and explicit bypasses remain unsupported pending architecture enforcement. Soft-delete restore is represented by its update diff. This hook does not implement hash-chain storage.

- Manifest permissions become Gate abilities only for the boot-time enabled set. Each authorization uses the current company and integer authenticated actor, then delegates to PermissionContract; missing context, undeclared ability and fallback provider deny. This is Gate plumbing, not the auth-rbac module: no super-admin bypass or implicit role grants are added. Business routes must explicitly apply company-context plus Laravel can middleware when implemented.

- The base ModuleServiceProvider derives ownership from `modules/<id>/Providers/` and loads only that enabled module's migrations, PHP/JSON translations and `routes/api.php`. API routes are mounted at `api/<id>` with `api`, `auth:sanctum` and `company.context`; every route must additionally declare a `can:` ability or provider boot fails. Disabled modules contribute none of these resources. Module providers overriding boot must call `parent::boot()`.

- Jalali support is a native arithmetic implementation of the published jalaali algorithm rather than morilog/jalali: upstream manifests for v3.4/v3.5 are published as `moree-dev/jalali`, Packagist identity and security advisories cannot be verified from this environment, and it adds `beberlei/assert` (ext-simplexml). Swapping to the package later only touches `App\Support\Values\Jalali`.
- Platform identity, token, queue and migration tables use the `core_` prefix. Users are global identities without `company_id`; memberships, roles and data scopes belong to multi-company/auth-rbac. Login/me/logout are the explicit public-route allowlist; all module routes need `can:`. Cache and sessions default to file storage for cPanel; queue defaults to database (`core_jobs`).
- Standalone platform test scripts are judged by exit code and a final `passed.` line because Laravel's console exception handler may exit 0.

- Numbering is a core service. Allocation must run inside the caller's business transaction so rollback releases the number (gap-free); counters are scoped by company, branch, fiscal year and the reset period implied by the finest date token. Default pattern `{jy}-{seq:6}` resets each Jalali year in the display timezone; `{seq:N}` pads but never truncates. Settings are stored as JSON per company/module/key, readable only for enabled modules and declared keys; money-like settings use the new `decimal` type (exact string, scale ≤4).

- Async event delivery uses the inbox row as the durable transactional record (written in the publisher's transaction on the same connection, so no separate outbox is needed); the after-commit database-queue job is only a low-latency trigger and the scheduled drain recovers missed triggers, retries and stale workers. Handler side effects and the processed mark commit together, giving exactly-once database effects per listener/event; external side effects must still be idempotent. Entries for listeners of disabled modules remain pending until the module is enabled. Defaults: 5 attempts, 30-second base exponential backoff capped at one hour, 15-minute stale lock, 30-day processed retention.

- Dataset providers supply only a definition (permission, typed column whitelist, optional source columns, company and scope columns) and a base query; the core registry centrally applies company filtering, permission, row scope, column/filter/sort/paging validation and never exposes write operations. DataScopeContract defaults to `none`; auth-rbac will provide real own/department/branch/all scopes. A scope level without a mapped column returns no rows. Text `contains` filters bind user values with literal `%`/`_` via `ESCAPE '!'`; identifiers come only from validated code definitions.

- AI gateway: effective enablement = factory `ERP_AI_ENABLED` AND not `AI_KILL_SWITCH` AND company module toggle (default manifest `enabled_default`, false) AND company capability toggle (default false) AND provider not `off`. Disabled calls return a clean Persian `disabled` result without usage/audit side effects so off mode never depends on optional engines. External calls fail closed without a positive remaining monthly company budget; costs use configurable per-1K token prices with exact decimals. Tools are read-only, manifest-declared, permission-bound handlers; the tool loop is limited to three rounds. Proposal accept/reject only records the decision; owning modules apply accepted proposals through their audited services. Python requests carry `X-ERP-Timestamp`, `X-ERP-Request-Id` and `X-ERP-Signature: sha256=HMAC(secret, timestamp\nrequest_id\nbody)`; the Phase 8 service must reject skew over 300 seconds and replayed IDs, and the secret must be at least 32 bytes.
